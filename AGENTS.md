## 1. Mission (read this twice)

IronGuard catches multi-turn text scams **before the strike**: the turn where the scammer sends the link or asks for money, a code or a gift card.

- **The model is the product.** Everything else (UI, agent, Photon) exists to show what the model does and act on it.
- **Dragonfly / PreyNet** is a causal sequence model. It reads a conversation turn by turn and forecasts where it is heading: scam family, next stage, and turns left until the strike. It reports calibrated, honest confidence.
- **Leaf Sheep / Chloroplasts:** when a new (zero-day) scam appears, Nemotron (the "algae") generates synthetic conversations. We train a small adapter head (a "chloroplast", tens of KB) in seconds. The phone downloads only that adapter and runs inference locally. **No customer text is ever used for training or sent to the cloud by default.**
- **Safeguard Agent:** Nemotron with real tool calls turns a forecast into protection: verify the claimed brand, number and domain, lock links, show safe next steps, and send anonymous reports to the reef.
- **Photon:** a real iMessage/SMS number. Users forward a suspicious thread and get the forecast and safe actions back in the same thread. This is an opt-in cloud mode.

The full model spec is in `docs/MODEL_SPEC.md`. **Do not invent model behavior that contradicts it.**

## 3. Golden rules for agents

1. **Contracts first.** Every request or response that crosses an ownership boundary is defined in `contracts/` (JSON Schema plus examples). Read the schema before writing code that sends or receives data. Never edit `contracts/` unless you are working for B. After **M0 (H1)**, contracts are **additive only**: you may add optional fields, never rename or remove.
2. **Build against mocks until the real thing lands.** Every service must work with its upstream dependency mocked: web works with `VITE_USE_MOCKS=1`, api works with `IRONGUARD_MODEL=stub`, and bridge works with `MOCK_API=1`. Mock data comes from `contracts/examples/`.
3. **Stay in your lane.** Don't reformat, "clean up", rename or upgrade anything you weren't asked to touch. Don't fix another area's failing check; report it in your progress file.
4. **No dependency upgrades.** Add new deps only inside your own service's manifest (`ml/pyproject.toml`, `api/pyproject.toml`, `web/package.json`, `bridge/package.json`). There is **no root** `package.json` or `pyproject.toml`, and you must not create one.
5. **Small commits on your branch, never on `main`.** Commit message format: `[A|B|C][P<phase>] <imperative summary>`, e.g. `[A][P2] add lock-on hysteresis to PreyNet inference`.
6. **Fixed ports:** api `8000`, web `5173`, bridge `8787`. Fixed env var names are listed in `.env.example`. Never hardcode secrets; never commit `.env`.
7. **No notebooks in git.** Use `.py` scripts. Scratch notebooks go in `ml/notebooks/`, which is gitignored.
8. **Privacy is a feature; don't break it.** The web app must never send message text over the network except during an explicit, user-confirmed report or in Photon mode. Never log raw message text to disk. In Photon mode, keep thread history in memory only.
9. **No fabricated numbers.** Every metric shown in the UI or pitch must come from `ml/artifacts/eval_summary.json`, generated by `make eval`. If a number doesn't exist yet, show `--`.
10. **End every task by updating your progress file** (`progress/<you>.md`): what you did, what you skipped, and what is unverified.

## 4. Plugins: ECC + Ponytail (how they coexist)

- **Ponytail** (`full` mode) is on while you **implement**: write the least code that works, use stdlib and existing deps first, and never skip validation, error handling, security or accessibility.
- **ECC** handles **workflow**: planning (`/ecc:plan`), fresh-context review (`/code-review`), build repair (`/build-fix`), checkpoints (`/checkpoint`), and context hygiene (`/context-budget`). In Codex, use ECC's skills (`$configure-ecc` and others).
- Before every PR, run **both** reviews on your diff: `/code-review` (correctness) and `/ponytail-review branch` (bloat). In Codex: `$ponytail:ponytail-review`.
- **Testing policy (overrides ECC's TDD defaults and Ponytail's minimalism):** tests are **required** for the contract validators, metric functions (`ml/ironguard_ml/metrics.py`), the data splitter (leakage), the PII scrubber, each agent tool function, and ONNX-vs-PyTorch parity. UI tests are **not required**. Keep each test small.
- Keep fewer than 10 MCP servers enabled. Run `/context-budget` if responses get slow or forgetful.

## 7. Git workflow for agents (T3 Code / Claude Code / Codex)

- Each agent thread works in its **own git worktree** on a branch named `<letter>/<feature>`, e.g. `a/preynet`, `b/safeguard-tools`, `c/hud`. A member runs at most **3 parallel threads**.
- Agents **never** push to `main`, never force-push, and never rebase another member's branch.
- The member merges finished worktree branches into their **member branch** (`a/main`, `b/main`, `c/main`) and opens **one PR to `main` per merge window**.
- Before committing, run `make validate` and your area's `make check-<area>`.
- If the pre-commit hook blocks you, **do not bypass it**. You touched a file you don't own: revert that file and write a Request instead.
